Factory Inventory Management System

A full-stack demo application for inventory tracking, order management, demand forecasting and spending analytics across three factory warehouses. Vue 3 single-page frontend, FastAPI backend, JSON files held in memory — no database.

Vue 3.5.44 FastAPI 0.162.0 Python 3.14.6 Vite 8.3.5 read-only data no auth

System Architecture

Two independent processes on different ports. The browser loads the SPA from the Vite dev server; every data request then goes directly from the browser to FastAPI over CORS — there is no proxy and no server-side rendering.

Data Flow

One path carries almost every interaction in the app — a filter change in the header re-fetching a view. Tracing it end to end explains the whole system.

1

User changes a filter

FilterBar.vue is mounted once in App.vue, above router-view, so it persists across navigation. Its selects are bound to refs from useFilters.

2

Shared refs update

Those refs live at module scope in composables/useFilters.js, not inside a component — so every view that imports useFilters() reads the same four values rather than its own copy.

3

The active view reacts

Each view watches the filter refs and calls its loader, which asks getCurrentFilters() for a plain object and maps the selected period onto the API's month parameter.

4

api.js builds the request

The matching method appends each filter to URLSearchParams, omitting any whose value is 'all', then issues a GET. The loader wraps the call in try/catch/finally and drives loading and error refs.

5

FastAPI filters in Python

Query params arrive as Optional[str] handler arguments. apply_filters() narrows the in-memory list by warehouse, category and status; filter_by_month() then matches order_date by substring, expanding a quarter into its three months.

6

Pydantic validates the response

response_model coerces and trims each record to its declared shape. A field present in the JSON but missing from the model is silently dropped — which is why model and fixture must change together.

7

View stores raw data, derives the rest

The response lands in a raw ref such as allOrders. Everything shown — totals, category rollups, chart geometry, top-product rankings — is a computed over that ref, cached until the data changes.

8

Render

Templates draw tables and inline SVG charts. Currency formatting follows the locale from useI18n, so switching language also switches USD to JPY.

Notes for Newcomers

Four things in the current tree are worth knowing before you start changing code. All were observed directly in the source, not inferred from documentation.

The frontend is ahead of the backend

Tasks and purchase-order features are fully built in the UI — TasksModal.vue (621 lines) and the create/view PO flow in Dashboard.vue — but no matching routes exist. Opening the dashboard logs a 404 from api.getTasks(). The backend has no write endpoints of any kind.

A referenced component does not exist

Dashboard.vue:289 renders <PurchaseOrderModal>, but there is no such file in components/ and no import for it. Vue logs "Failed to resolve component" on every dashboard render and the element silently renders nothing.

Backlog.vue is orphaned

The view exists and is complete, but main.js registers only six routes and none of them point at it. Backlog data instead reaches the user through a section of the dashboard. The file is reachable only by adding a route.

Write-path scaffolding is half-present

main.py defines a CreatePurchaseOrderRequest model that no handler consumes, and purchase_orders.json is an empty array. The /api/backlog handler already joins a has_purchase_order flag against it, so the read side of the feature is wired and waiting.
